# 优化开发经验手册（Playbook）

> 本文档把本次 avatar-chatbot 重构中可复用的方法沉淀为通用原则，用于指导**任何"接手一个能跑但粗糙的存量项目并做深度优化"**的工作。
> 与本项目具体细节无关的部分刻意抽象成方法论；举例来自本项目，仅作说明。
>
> 阅读顺序建议：第 1 节（原则）→ 第 2 节（流程）→ 第 5 节（假实现识别）→ 第 9 节（Checklist 直接抄）。

---

## 0. 适用场景

| 场景 | 是否适用 |
| :--- | :--- |
| 接手别人的 MVP / 早期项目，要做"能用 → 好用 → 好看" | ✅ 核心场景 |
| 自己半年前写的小项目要重启 | ✅ |
| 老项目要加新功能，但结构已经撑不住 | ✅ |
| 从零开始的新项目 | ⚠️ 部分适用（第 1、3 节可直接用） |
| 大型团队协作、有专职 PM/QA | ⚠️ 流程需按团队裁剪 |

## 1. 十条原则

### P-01 先让它跑起来，再谈重构

**为什么**：不建立可复现的基线，就无法判断"改坏了"还是"本来就坏"。
**怎么做**：克隆 → 读 README 按图索骥 → 起服务 → 记录**当前真实行为**（截图/录屏/请求日志）。基线里"跑不起来"的部分，本身就是第一个审查发现。
**反例**：直接大改代码，最后不知道白屏是自己引入的还是原本就有。

### P-02 审查要"证据化"，不要"印象化"

**为什么**：`"这个函数写得不太好"` 无法行动，也无法验证是否修好。
**怎么做**：每条发现都要有 `文件:行号 + 代码片段 + 复现方式 + 影响`。行号基于**被审查的那个 commit**，并在文档开头写明 commit id。
**收益**：三个月后回看仍能定位；评审时可以逐条核对。

### P-03 区分"功能缺陷"与"实现空转"

**为什么**：最危险的 bug 不是崩溃，而是**看起来在工作、实际什么都没做**（详见第 5 节）。
**怎么做**：对每个"已实现"的特性问一句："有可观测的证据证明它生效吗？" 没有证据的，按缺陷处理。

### P-04 决策必须留下"被否决的选项"

**为什么**：后人重复讨论同一件事的成本极高；而"为什么不用 X"往往比"为什么用 Y"更重要。
**怎么做**：决策记录固定五段：**背景 / 选项对比 / 决策 / 理由 / 代价**；被否决的方案单独进"未采纳方案"清单，写清否决原因。
**判据**：如果三个月后有人问"为什么不用 Tailwind"，文档能直接回答，说明记录合格。

### P-05 文档按"读者的问题"拆分，不按"内容主题"拆分

一份文档只回答一类问题，否则会越写越长、没人维护。

| 读者想知道 | 文档 | 时态 |
| :--- | :--- | :--- |
| 原来哪里不对？ | AUDIT / 审查报告 | 过去 |
| 为什么现在是这样？ | DECISIONS / 决策与动作日志 | 过去→现在 |
| 现在代码怎么组织？我该改哪？ | ARCHITECTURE / 架构说明 | 现在 |
| 下一步做什么？ | ROADMAP / 路线图 | 未来 |

**反模式**：一份 `docs/开发文档.md` 里同时塞架构、变更、待办、踩坑——半年后无人敢改。

### P-06 每层都要有降级路径

**为什么**：玩具项目最常见的失败不是"慢"，而是"一个外部依赖挂了就整站白屏"。
**怎么做**：为每个不可控依赖设计降级：无 API Key → 离线话术；生图超时 → 本地程序化图；3D/WebGL 库缺失 → CSS 占位；TTS 不支持 → 静默跳过。
**检验**：断网、删 Key、删运行时文件，三种情况下 UI 是否仍可用（只是能力降级）。

### P-07 协议即契约，改协议必须同步三处

**为什么**：前后端/模块之间真正耦合的是**数据形状**，不是函数名。
**怎么做**：把事件/字段列表写成表格进架构文档；改协议时同步：① 生产方 ② 消费方 ③ 文档。缺一处就会在下次迭代踩坑。
**建议**：给协议加版本号或用"新增字段而非改字段"的兼容策略。

### P-08 提交历史要能讲出故事

**为什么**：`git log` 是最便宜的项目史；一次性 `update` 提交等于放弃这份资产。
**怎么做**：按**主题**分批提交（后端 / 前端结构 / 视觉 / 修复 / 依赖清理 / 文档），message 用 `type(scope): 做了什么`；无法逐 commit 可构建时不要硬拆，在 PR 描述里说明原因。
**配套**：用 tag 固化"重构前"快照，`git diff v0.5.0..v1.0.0` 就是完整重构 diff。

### P-09 重构前先建"安全网"，没有测试就建"临时安全网"

**为什么**：深度重构必然改坏东西，区别只在于你是否提前发现。
**怎么做**：有测试就跑测试；没有就写一次性冒烟脚本（无头浏览器 / jsdom / curl 脚本），至少覆盖"页面能渲染 + 主流程能跑通"，重构期间反复执行。
**注意**：临时脚本不必入库，但要在文档里记录"做过什么验证"（否则等于没验证）。

### P-10 优化要"可量化"

**为什么**："更流畅了"不是结论，"首字延迟 3.2s → 0.4s"才是。
**怎么做**：改前记录基线（体积 / 延迟 / 请求数 / 帧率），改后同口径复测，写进验证记录表。
**最低要求**：构建体积、首屏渲染时间、关键接口耗时、依赖数量，四项至少各一条。

## 2. 接手存量项目的标准流程

```
① 建基线（Day 0）
   克隆 → 按 README 跑通 → 记录真实可用度 → 截图/录屏
   ★ 跑不通的地方 = 第一批缺陷

② 全量通读（不要边读边改）
   后端：入口 → 路由 → 业务 → 外部依赖 → 配置
   前端：入口 → 页面 → 组件 → 状态 → 请求
   工程：依赖声明、构建配置、CI、仓库卫生
   ★ 只记录，不动手，避免"改一半"的状态

③ 建立问题台账
   编号 + 严重级 + 位置 + 证据 + 影响 + 状态
   严重级：P0 阻断/白屏、P1 核心功能不成立、P2 体验质量、P3 代码卫生
   ★ 台账是后续所有工作的索引

④ 定向验证（把"怀疑"变成"事实"）
   对每个 P0/P1 写一条最小复现：curl / 断网 / 删配置 / 注入异常
   ★ 复现不了的，降级或删除，不要留在台账里制造噪音

⑤ 定架构与契约
   先定"模块边界 + 数据流 + 协议"，再动手写代码
   把决策写进 DECISIONS（含被否决方案）
   ★ 此时应能回答："我要改的这行代码属于哪一层？"

⑥ 分批实施 + 每批验证
   按依赖顺序：底层（配置/适配器）→ 业务 → 接口 → 展示 → 样式
   每批结束跑一次构建 + 冒烟，记录验证结果
   ★ 不要等全部改完再验证

⑦ 收尾：文档、历史、路线图
   审查报告定稿 → 决策与动作记录补齐 → 架构文档 → 路线图（带验收标准）
   tag 快照 → 分支 → 语义化提交 → 版本 tag
```

**时间分配经验**：如果总预算 100%，②③④（读懂 + 立案 + 验证）应占 30~40%。跳过这一步直接写代码，返工率会超过节省的时间。

## 3. 文档体系模板（可直接复用）

### 3.1 四文档模型

| 文档 | 必备章节 | 更新时机 |
| :--- | :--- | :--- |
| `AUDIT.md` | 概览统计 → 问题台账（分域）→ 关键问题根因 → 复现方法 | 审查结束时冻结；修复状态列随进度更新 |
| `DECISIONS.md` | 文档约定 → 决策（D-xx）→ 动作（A-xx）→ 验证（V-xx）→ 未采纳（N-xx） | 每次决策/每批改动后追加 |
| `ARCHITECTURE.md` | 全局图 → 目录职责 → 数据流 → 接口契约 → 配置矩阵 → 扩展指南 → 已知限制 | 结构或协议变化时 |
| `ROADMAP.md` | 版本规划 → P0/P1/P2 待办（含验收标准）→ 技术债 → 维护约定 | 每次规划/完成时 |

**可选第五份**：`PLAYBOOK.md`（本文）——跨项目可复用的方法论。它的价值不在记录"这个项目做了什么"，而在"下次换个项目还能用"。

### 3.2 编号规范

```
B-xx  后端问题      F-xx  前端问题      E-xx  工程/仓库问题
O-xx  优化点        D-xx  决策          A-xx  动作
V-xx  验证          N-xx  未采纳方案    R-xx  路线图事项
```

**规则**：只追加不重排（避免外部引用失效）；推翻旧决策时新增 D 并注明 `取代 D-xx`。

### 3.3 决策条目模板

```markdown
### D-xx 一句话结论（动词开头，可判断）

**背景**：什么问题逼出了这个决策？
**选项**：A / B / C 各自优缺点（表格最佳）
**决策**：选了什么
**理由**：为什么（1~3 条，可验证）
**代价与风险**：牺牲了什么，什么情况下会失效
**关联**：F-xx / B-xx
```

### 3.4 验证记录模板

```markdown
| ID | 验证项 | 命令 / 方法 | 结果 |
| V-01 | 前端构建 | npm run build | ✅ 185 kB + 999 kB（已拆包） |
| V-10 | 反向验证 | 删掉运行时后加载 | ❌ 复现白屏，证明问题成立 |
```

**要点**：不仅记录"改好了"，也记录"**能复现原问题**"。反向验证是审查可信度的来源。

## 4. 审查清单

### 4.1 后端

- [ ] 配置缺失时能否启动？（必填项、import 时求值、默认值）
- [ ] 外部调用是否有超时/重试/降级？
- [ ] 流式接口是否"真流式"？（首字延迟 vs 整段耗时）
- [ ] 多轮对话的上下文如何传递？会被谁裁剪？
- [ ] 工具调用：并行调用、参数传递、失败处理、轮次上限
- [ ] 用户输入是否有长度/类型校验？危险操作（eval/exec/SQL）是否白名单？
- [ ] 错误是否会泄漏内部细节给前端？
- [ ] 日志：结构化？有 request id？还留着 `print`？
- [ ] CORS/鉴权/限流是否与部署场景匹配？
- [ ] 单例对象是否被重复创建（客户端、缓存）？

### 4.2 前端

- [ ] 是否存在"构建通过但运行白屏"的隐患？（库在模块顶层校验全局变量）
- [ ] 静态 import 的重型依赖能否懒加载？
- [ ] 样式是否有模板残留/全局污染？
- [ ] 请求是否可中断？错误是否可恢复？
- [ ] 状态是否持久化？刷新后用户损失多大？
- [ ] 是否有响应式？窄屏可用吗？
- [ ] 语音/媒体等浏览器 API 是否有能力探测与降级？
- [ ] 第三方库的 API 用法是否**真实存在**（对照类型定义）？
- [ ] 长列表/流式渲染是否有性能陷阱？
- [ ] 无障碍：aria、键盘操作、`prefers-reduced-motion`

### 4.3 依赖与工程

- [ ] 声明的依赖版本能否在**当前运行时**安装运行？（Node/Python 版本）
- [ ] 有没有声明了但代码里不存在的模块（如 electron 目录）？
- [ ] 有没有未使用的依赖？
- [ ] lint 是否真的能跑？（配置 API 与插件版本匹配）
- [ ] 构建缓存/产物是否被提交进仓库？
- [ ] README 的结构图与真实目录是否一致？
- [ ] 有没有测试？没有的话，最小冒烟怎么做？

### 4.4 仓库与文档

- [ ] `.gitignore` 是否覆盖 `.env` / 构建产物 / 虚拟环境？
- [ ] 示例请求体（body.json）与当前 schema 是否一致？
- [ ] README 的启动步骤是否**验证过**？
- [ ] 许可证与素材（模型/字体/图片）的授权是否清楚？

## 5. "假实现"识别手册（最高价值的一节）

> 存量项目里最难发现、也最伤信任的，是"代码写了、UI 有了、实际没生效"。
> 以下六种模式，命中任意一条都要挖到底。

### 5.1 空转的 try/catch

```js
try { instance.setParameterValueByName(name, value); } catch (e) { /* ignore */ }
```
**症状**：功能"从不报错"，但也"从没效果"。
**识别**：搜索 `catch` 里只有注释/空语句的位置；逐个确认被调 API **是否真实存在**（对照 `.d.ts` / 文档 / `typeof fn === 'function'`）。
**修法**：能力探测 + 多级回退（Cubism4 API → Cubism2 API → 无操作），并把"不支持"暴露成可见状态。

### 5.2 假流式

```python
content = await non_stream_call(...)   # 等整段生成
for ch in content: yield ch            # 再逐字符吐
```
**症状**：UI 有打字机效果，但首字延迟等于全量耗时；流量是"突发"不是"涓流"。
**识别**：看首字节时间（TTFB）与总耗时是否接近；看 `stream=True` 是否真的传了。
**修法**：用真正的流式接口；需要结构化数据（工具调用）时，**在流里增量累积**，而不是退回非流式。

### 5.3 写了但没接线

**症状**：`adapters.chat_stream()` 实现完整、文档也写了，但全项目没有一处调用。
**识别**：对每个"看起来是核心能力"的函数 grep 调用点；为 0 的就是死代码或未完成功能。
**修法**：要么接上，要么删掉并在文档里说明。

### 5.4 用错库的 API（靠 try/catch 掩盖）

**症状**：参数名对、方法名"看起来对"，但库根本没有这个方法。
**识别**：读 `node_modules/<pkg>/dist/**/*.d.ts` 或 Python 包 `__all__`，而不是凭记忆。
**教训**：名字听起来合理的 API（`setParameterValueByName`）最容易骗过 review。

### 5.5 假的"已完成"标记

**症状**：README 勾选了"支持 Electron 打包"，仓库里却没有 `electron/`；"支持多模型"但只有一套素材。
**识别**：把 README 的每个 ✅ 当作待验证断言，逐条找代码证据。
**修法**：文档与代码同源——能跑的才写"支持"，其余移到路线图。

### 5.6 静默失败的持久化

```js
try { localStorage.setItem(k, v) } catch { /* 忽略 */ }
```
**症状**：用户以为保存了，刷新后丢失（常见于配额超限、隐私模式）。
**识别**：构造大对象写入、检查返回值与 `storage` 事件。
**修法**：失败要有用户可见反馈 + 容量治理策略（截断/清理/提示）。

## 6. 重构手法

### 6.1 分层：先切"变化原因"，再切"文件"

不要按"行数"拆文件，按**变化原因**拆：协议变 → service；状态机变 → hook；视觉变 → 组件/样式；常量变 → config。
判据：一个文件里的代码，是否会在**不同的时机、因为不同的理由**被修改？

### 6.2 状态归属：能下沉就下沉，需共享才上提

- 只影响一个组件 → 组件内 state
- 影响兄弟组件 → 提升到最近公共父级
- 影响全局（主题、Toast、用户）→ Context
- 需要跨刷新保留 → 持久化 hook

反例：把"输入框内容"放进全局 store，导致任何输入都触发全应用重渲染。

### 6.3 契约先行

改前后端交互时，**先写事件/字段表**，再分别实现两端。表就是验收标准，也是文档素材。

### 6.4 降级设计三问

1. 这个依赖挂掉时，用户看到什么？
2. 降级路径本身会不会再挂？（兜底要有兜底）
3. 用户能否知道"现在是降级状态"？（顶栏状态徽章 / 提示条）

### 6.5 视觉重做：令牌先行

先定 CSS 变量（颜色/圆角/阴影/间距/字体），再写组件样式，最后做动效。
好处：换主题只改变量；避免"每个组件各写一套颜色"导致的风格漂移。
**二次元/游戏化风格**的三个高性价比手段：① 场景化背景（渐变 + 粒子）② 玻璃拟态面板 ③ 微交互（悬停位移、打字机、呼吸动画）。三者成本低、观感提升大。

### 6.6 提交拆分：宁少勿碎

拆到"每个 commit 能说清一件事"即可。**不要为了凑数量强行按文件拆分**——如果 A 文件的改动依赖 B 文件的改动，就放同一个 commit。
拆分的目的是**可 review / 可回滚**，不是好看。

## 7. 提效技巧

### 7.1 网络不稳时的依赖安装

- 换镜像源（npmmirror / 清华 PyPI），并**在提交前把 lockfile 里的镜像地址改回官方源**，否则会污染他人环境。
- 加 `--ignore-scripts` 先装完树，再单独处理需要的 postinstall。
- **原生二进制被截断**的典型症状：`Bus error (core dumped)`、`SIGBUS`、文件体积明显偏小（如 esbuild 应为 ~10MB）。修法：单独重装该平台包或直接 curl tarball 覆盖。
- 判断是不是二进制损坏：单独执行 `node_modules/.bin/<tool> --version`，能跑就说明二进制 OK，问题在别处。

### 7.2 没有浏览器时怎么验证前端

- 用 esbuild 把入口打成 IIFE，配合 `jsdom` 在 Node 里跑真实 React 渲染；
- 需要补的全局：`TextEncoder/TextDecoder`、`matchMedia`、`scrollTo`（jsdom 未实现）、`fetch`（打桩）；
- 断言"选择器存在 + 关键交互后的 DOM 变化"，比"截图"更适合无头环境；
- 这类脚本**不必入库**，但验证结论必须进 `DECISIONS.md`（V-xx）。

### 7.3 复现外部依赖故障

- 断网模拟：把超时调到 1s，或指向不存在的 host；
- 缺失配置：临时改名 `.env`；
- 缺失运行时：临时重命名静态文件，观察是否白屏；
- **反向验证**（证明问题存在）与**正向验证**（证明已修复）成对记录，可信度最高。

### 7.4 处理"跑不起来的基线"

先修构建/启动（版本不匹配、缺依赖），再谈功能。**构建问题优先于业务问题**，否则所有验证都无从谈起。

### 7.5 大文件改写策略

整文件重写（Write）适合结构彻底变化；局部修改（Edit）适合保持历史 blame 可读。
**经验**：如果一个文件超过 70% 的行都要改，直接重写，不要用几十次 Edit 拼。

### 7.6 密钥卫生（最容易出事的五分钟）

**常见事故**：把 Key 填进 `.env.example`（模板会被提交）、`git add -A` 时顺手带上 `.env`、
把 Key 写进 README 示例、把带 Key 的截图/日志贴到 issue。

**最小防护组合**（成本几乎为零）：

1. **模板与实例分离**：仓库只提交 `.env.example`（占位符），真实值只写 `.env`；
2. **忽略规则覆盖变体**：`.env`、`.env.*` 全覆盖，再用 `!.env.example` 显式放行模板；
3. **提交前拦截**：pre-commit 扫描暂存内容里的 `sk-[A-Za-z0-9]{20,}` 与 `.env` 实例文件；
4. **随时自查三条命令**：
   ```bash
   git check-ignore -v backend/.env      # 忽略规则是否生效
   git log --all -- backend/.env         # 是否曾被提交
   git grep -nE 'sk-[A-Za-z0-9]{20,}'    # 追踪文件中是否存在密钥
   ```
5. **泄露即轮换**：只要 key 出现在提交、截图、聊天记录、构建产物里，就当作已泄露——
   吊销并重新生成。删除文件、`git filter-repo` 都救不回已被别人拿到的密钥。

**心态**：钩子是"降低概率"，不是"安全保证"。真正的安全边界是**密钥可轮换 + 最小权限 + 定期检查**。

**同时注意**：排查密钥问题时，终端命令不要 `cat .env`；用"长度 + 掩码"的方式确认即可
（`len=35 sk-*******a63`），避免密钥被写进日志、截图或对话记录。

## 8. 反模式清单

| 反模式 | 后果 | 替代做法 |
| :--- | :--- | :--- |
| 一次性大提交 `update` | 无法回滚、无法 review、无法 bisect | 按主题分批 + 语义化 message |
| 文档只写"做了什么"不写"为什么" | 后人推翻又重建，循环返工 | 决策记录写选项与代价 |
| 只记录成功路径 | 无法判断修复是否真的有效 | 增加"反向验证"记录 |
| 为凑数强行拆 commit | 中间提交不可构建，bisect 失效 | 宁少勿碎，按依赖顺序 |
| 在 UI 层做协议解析 | 同一逻辑散落多处 | 协议解析收敛到 service |
| `alert()` 当错误处理 | 阻塞、不可样式化、移动端体验差 | Toast + 可恢复操作 |
| 全局 CSS reset + 模板残留 | 布局莫名受限 | 令牌化 + 删除死样式 |
| 把所有状态塞进全局 store | 全应用重渲染 | 就近原则 + Context 分层 |
| 假设第三方库行为不变 | 升级即崩 | 能力探测 + 契约测试 |
| 用 mock 掩盖外部依赖 | 上线才发现不可用 | 至少保留一条真实链路冒烟 |
| 只用手写假数据测流式 | 协议对了，但模型输出格式偏离（如少写前缀）会直接泄漏到 UI | 真实模型至少跑一轮，异常格式写进解析器用例 |
| 把密钥写进 `.env.example` | 模板被提交 → 密钥公开 | 模板只放占位符；用 pre-commit 拦截 |
| 排查密钥时 `cat .env` | 密钥进入日志/截图/对话记录 | 只看长度与掩码 |

## 10. 本文档如何演进

- 每次项目结束，新增一节"本次新学到的"，或把新原则补进第 1 节（编号递增，不重排）；
- 原则要可证伪：能举出反例，说明它还不够具体；
- 与本项目强相关的细节不要写进来——那些属于 `ARCHITECTURE.md` 与 `DECISIONS.md`。

> 一句话总结：**把"为什么"留在文档里，把"是什么"留在代码里，把"下一步"留在路线图里。**
